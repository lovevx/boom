## 一、One-pager（一页纸项目简介）

**一句话定位**
一款 2D 休闲「破坏 + 挂机」游戏：玩家用锤子砸楼赚金币，升级锤子与经济，逐步解锁自动轰炸炮台，从"手动破坏"平滑过渡到"自动化挂机"，越玩越省力。

**核心玩法循环**
`手动锤砸 → 赚金币 → 升级（锤子/经济/炮台）→ 解锁自动轰炸 → 更大范围破坏 → 赚更多金币 → 转生换永久加成`

**目标体验（首 30 秒）**
- 第一反应：玩法简单，砸楼有爽感（震屏 + 碎屑飞散 + 金币弹出）。
- 30 秒内理解完整闭环并完成首次升级，明显感觉"变强了"。
- 中期"第一颗炸弹爆炸"建立破坏爽感，自动化炮台让玩家从手动中解放。

**设计亮点（可直接在面试展开的点）**
1. **手动→自动化的成长曲线**：锤子先作为唯一手段，炮台作为机制型升级项解锁，1 台 → 多台自动轰炸，让"省力"成为成长反馈本身。此谓传统放置类"从手动退居辅助"的经典结构。
2. **无限层物理级联破坏**：建筑是无限层物理塔，任意方块被毁后上方整列失去支撑，作为独立刚体真实下落再吸附回位，破坏反馈有"真实物理级联"的层次感，而非一次性塌平。
3. **双层数值成长公式**：单局升级以加法为主、转生永久加成以百分比为主，两层层叠相乘（`(基础 + 加法) × 转生乘和`），同时保证"每个属性都能成长"和"长线平衡不膨胀"。此原则显式要求数值线与机制线并存，避免技能树退化成纯解锁。
4. **破坏反馈统一为"粉碎"而非"掉落"**：全项目统一用碎屑飞溅 / 破碎特效，不做掉落物品设计，保证破坏手感的一致性。

**当前状态**
可玩的垂直切片，核心循环完整可跑通；**转生 · 永久技能树已全链路实装**（RP 结算、三大方向永久技能树面板、转生按钮 + 二次确认、存档槽），留存闭环完整；仅离线收益等长线项按规划暂不实现。美术素材为工程演示用素材，属计划内的美术方向示例。

**工程规模**
- 引擎 Godot 4.7.2（2D / GL Compatibility / Jolt 物理），1920×1080。
- 10+ 独立模块、12 张材质贴图 + shader 质感分类、33 帧炮台待机动画、双 BGM 轮播。
- 做了分帧实例化等性能优化，解决场景切换主线程卡顿。
- 配套近 20 篇设计文档（含标准 GDD、数值、拆解、AI 提效工作流、复盘），闭环完整。

**个人作品 · Boomame —— 2D 挂机破坏游戏（Godot 4.7，独立完成设计与开发）**

- 独立完成从玩法设计、数值平衡到 Godot 4.7 开发落地的完整闭环，搭建无限层物理破坏玩法：任意方块被毁后上方整列真实物理级联塌落并吸附回位，给破坏提供层次感。
- 设计并落地"手动→自动化"成长结构：玩家先用锤子点击，通过机制型升级项逐步解锁自动轰炸炮台（1 台至多台），让"省力与挂机变强"成为成长反馈核心。

- 全程以设计文档 + 实现 + 实测迭代方式推进，产出近 20 篇设计与过程文档（含标准 GDD、数值、拆解、AI 提效工作流）并持续记录测试结论（EXPERIENCE）。
- 产出**标准 GDD**（概述 / 核心玩法 / 系统 / 数值 / 美术 / 里程碑），并在每个核心部分附「设计决策 + 迭代过程」手记，能把设计与落地过程按章讲清楚。

## 四、面试讲解结构（5 分钟版，按序讲）

面试官通常让你"介绍一下你的项目"。以下是一个亲测好用的递进结构，带着**目的**而不是流水账：

1. **一句话讲清它是什么**（10 秒）——用了 One-pager 的一句话定位。
2. **为什么做挂机/破坏这个切入点**（30 秒）——破坏反馈直接、爽感强、实现可控，适合验证"手动→自动化"这条我想练的成长设计；同时拆过同类 What the Buck?!，学的是方法而不是抄数值（可引用 docs/Reference_WhatTheBuck.md）。
3. **讲一个设计亮点 + 一个真实取舍**（2 分钟）—— 挑一两个"设计亮点"展开：
   - 例 A：物理级联破坏——一开始做成"整层整体下坠"，后来改成"每列物理级联 + 自动补层"，因为整体下坠缺层次、掩盖破坏反馈；改成多块独立刚体后破坏更真实，也为"补层顺序"带来新的处理逻辑。
   - 例 B：双层数值公式——为什么单局用加法、转生用百分比（避免同样倍率两处相乘导致指数爆炸），用 `sqrt` 限制转生点收益防止无限刷。
4. **讲一次从失败里学到的东西**（1 分钟）——见下方"设计复盘"，挑一个有数据支撑的。
5. **收尾留互动**（30 秒）——"我可以现场演示 / 展开讲任意一个子系统。"

> 别背稿。把这 5 段当作"主干路标"，每段准备 1–2 句撑住，其它靠和面试官问答自然延展。

## 五、可讲的设计复盘（面试"你有什么教训/取舍"专用）

> 以下都是本项目**真实发生过**的问题与处理，有据可查，可直接给面试官看。挑 1–2 个讲，讲时给"现象 → 定位 → 处理 → 结果"，别只讲结论。

**复盘 1｜同步加载导致切场卡顿 → 分帧实例化**
- 现象：从主菜单切进游戏时主线程卡顿（约几百 ms）。
- 定位：进入场景要一次性实例化 360 个 RigidBody2D 建筑方块并配置物理，同步阻塞主线程。
- 处理：改成**每帧生成 24 块、共 15 批**的分帧实例化，且自下而上生成，保证地面支撑与塌陷目标尽早可用。
- 结果：消除了切场冻结；顺带证明了"性能不只是引擎的事，也影响玩家首次体验的顺滑感"。

**复盘 2｜物理回调栈内改物理状态报错 → 延迟到物理步结束**
- 现象：炸弹爆炸回调里同步 `add_child()` 新刚体 / 改 `freeze` 会触发引擎报错（`body_set_shape_disabled`）。
- 定位：处于 `flushing queries` 阶段，此时改物理状态不安全。
- 处理：把重建 / 压实 / 补层统一 `call_deferred()` 推到物理步结束后执行。
- 结果：稳定不再报错。**延伸点**：放在策划语境，这让我养成了"改物理前先想清楚时机"的习惯，也理解代码边界其实来自游戏机制的物理层面。

**复盘 3｜数值改造用"白模验证"而不是拍脑袋**
- 现象：要改点击 CD 与转生基准这些手感/经济敏感参数。
- 处理：先按 `SPEC.md` 的节奏锚点（挡 0 TTK 甜区、锤速 Lv2 后 CD 是否贬值）定标，再动 `Hammer.attack_speed / MIN_COOLDOWN`，并把结果回填测试记录（EXPERIENCE.md 2026-08-25 记录）。
- 结果：参数有明确预期再改动，避免数值越调越乱。展示你会"用文档 + 验证约束改动"。

> 若要显得更有"数据感"，可补一句你实测的节奏数据（如首次转生约 X 分钟）。当前文档锚定 30 分钟单局、首次转生 ~18 分钟可得 1–2 RP，可作为你实测待回填的基线。
